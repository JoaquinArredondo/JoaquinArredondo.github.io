01 / Project Overview

Restoring color to a kingdom built from the rendering pipeline up.

CMYKingdom places the player in a magical world that has lost its color. The player explores the environment and collects cyan, magenta, and yellow crystals to bring color back to the kingdom.

Rather than relying on a commercial engine for rendering, our five-person team built the experience in a custom C++ and OpenGL engine. The project required us to connect low-level graphics systems with gameplay, tools, animation, physics, audio, and a large navigable environment.

03 / Terrain Pipeline

From Unity terrain tools to a custom OpenGL renderer.

Unity was used as a terrain-authoring tool, not as the final runtime. The authored data was exported and reconstructed inside our own engine.

  1. 01

    Sculpt the world

    Shape the kingdom's large-scale mountains, valleys, coastlines, and traversal spaces with Unity's terrain tools.

  2. 02

    Author surface regions

    Paint terrain layers and prepare splatmap channels that describe where grass, rock, sand, and other materials should appear.

  3. 03

    Export heightmaps and splatmaps

    Convert the authored terrain into data the custom engine can load rather than depending on Unity at runtime.

  4. 04

    Generate terrain geometry

    Use height values to construct the terrain mesh and support a matching heightmap collider for player movement.

  5. 05

    Blend materials in GLSL

    Sample the exported splatmaps in the terrain shader and blend multiple textures across a single continuous landscape.

  6. 06

    Populate and iterate

    Add instanced grass and environment assets, then revise density, composition, and readability while testing the world in motion.

04 / Instanced Vegetation

Adding motion and density without multiplying draw calls.

Grass helped make the terrain feel alive, but a large landscape can contain far more repeated geometry than is practical to render object by object.

The grass shader used instanced rendering to reuse the same vegetation geometry across many placements. The result was a denser environment with animated wind movement while preserving a rendering approach appropriate for a real-time project.

Technical focus Repeated geometry, data-driven placement, shader animation, and real-time performance.

05 / Engine Context

My systems operated inside a broader team-built engine.

The environment depended on many systems created collaboratively by the full team. This context is important: terrain rendering was not an isolated demo, but one part of a complete interactive graphics application.

Scene Architecture

Component-based objects, transform hierarchies, cameras, and lights.

Render Pipeline

Modular render passes, deferred rendering, HDR, skybox rendering, and water refraction.

Lighting

Cascade shadow mapping with filtering techniques for soft shadows across a large world.

Tools

An in-game level editor for object selection, component editing, and scene saving and loading.

Interaction

Bullet Physics integration, terrain collisions, a player controller, power-ups, and UI.

Character Systems

Skeletal animation, animation blending, Assimp asset loading, and audio integration.

08 / Reflection

Understanding what a game engine normally hides.

CMYKingdom made the graphics pipeline tangible. Features that are normally a checkbox or built-in component became explicit systems involving data, buffers, shaders, transforms, draw calls, and tradeoffs.

The project also clarified why I am drawn to technical art. Designing an environment was only half of the challenge; I also needed to build a reliable way for the engine to interpret that design. The most rewarding work happened where visual goals and technical constraints directly informed one another.

The goal was not only to render terrain. It was to preserve an artistic direction while building the systems that made the world possible in real time.
